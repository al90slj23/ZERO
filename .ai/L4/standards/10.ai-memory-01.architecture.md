# 10.ai-memory-01.architecture - AI 记忆体系架构规范

> **文档版本**：v2.0.0
> **创建日期**：2026-07-18
> **最后更新**：2026-04-16
> **定位**：定义 `.ai/` 七层蒸馏记忆体系的层级划分、边界定义、读写流程

---

## 核心理念

### 人类架构师 + AI 开发者

```
人类 = 架构师 + 规范师 + 审查者（写 WHAT + WHY）
AI   = 开发者 + 执行者 + 提议者（做 HOW + 写日志）
```

### 蒸馏金字塔

信息从下往上逐层蒸馏提纯，从上往下逐层展开追踪。每一层是下一层的精华提取。

```
L0  最精简（纯索引）     ← 蒸馏方向（从下往上提取精华）
L1  ...
L2  ...
L3  ...
L4  ...
L5  ...
L6  最完整（操作日志）   → 展开方向（从上往下追踪细节）
```

### 工具无关

`.ai/` 目录是独立体系，不包含任何工具专属文件（无 `CLAUDE.md`、`AGENTS.md`、`.cursorrules` 等）。所有工具专属入口文件由同步脚本生成或链接。

## 七层定义

### 总览

```
L0   SPECS         项目进度管理   动态层              "当前在做什么"
L1   OVERVIEW      启动引导       1个文件，≤100行      "项目概览+零容忍规则"  → AGENTS.md / CLAUDE.md 等
L2   INDEX         分类索引       11个文件，≤50行/文件  "去哪找规范"          → .kiro/steering/ 等（逐文件链接）
L3   CONDENSED     精炼规范       ~60个文件，100-150行  "怎么做对"            → .cursor/rules/ 等（整目录链接）
L4   FULL          完整规范       无限制               "为什么这么做"
L5   LOG           操作日志       无限制               "做过什么"
L6   GRAPH         知识图谱       无限制（可选）        "语义搜索+历史积累"
```

### 信息密度与读取频率

```
层级    信息密度（从导航到完整）          AI 读取频率
L0     ██░░░░░░░░  进度/规格              ░░░░░░░░░░░░  按需（开发功能时）
L1     ████░░░░░░  概览+零容忍规则         ████████████  每次对话（自动载入）
L2     ██████░░░░  分类索引               ████████████  每次对话（Kiro 自动载入）
L3     ████████░░  精炼规范（≤200行）       ████████░░░░  按 scope 匹配（自动载入）
L4     ██████████  完整规范               ██░░░░░░░░░░  需要完整信息时（手动读取）
L5     ██████████  原始事实记录           ░░░░░░░░░░░░  回溯历史时（极少）
L6     ██████████  语义搜索               ████░░░░░░░░  精准获取相关片段（可选）
```

### L0 — SPECS（项目进度层）

**角色**：工作台

| 维度 | 定义 |
|------|------|
| 内容 | 功能规格（active/backlog/completed）、工作流、钩子、模板 |
| 不放什么 | 通用规范（→L3/L4）、操作日志（→L5） |
| 加载方式 | 通过 symlink 映射到各 IDE 的 specs/projects/features/tasks 目录 |
| 谁维护 | 人类写需求，AI 写设计和任务 |
| 更新频率 | 高（功能开发周期内） |

**Spec 四文档**：
| 文件 | 谁写 | 内容 |
|------|------|------|
| `00.spec-01.requirements.md` | 人类 | WHAT — 需求 + 验收标准 |
| `00.spec-02.design.md` | AI | HOW — 技术设计方案 |
| `00.spec-03.tasks.md` | AI | DO — 实施步骤 + checkbox |
| `00.spec-04.decisions.md` | 人类确认 | WHY — 设计决策及理由 |

---

### L1 — OVERVIEW（启动引导层）

**角色**：项目名片

| 维度 | 定义 |
|------|------|
| 内容 | 零容忍规则 + 技术栈 + L2 分类索引速查（三合一） |
| 不放什么 | 具体规范细节（→L3）、完整文档（→L4） |
| 行数 | ≤100 行，**只有 1 个文件** |
| 文件名 | `00.overview.md` |
| 加载方式 | symlink 到 `AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`.windsurfrules` 等 |
| 谁维护 | 人类架构师 |
| 更新频率 | 低 |

**边界测试**："如果 AI 不知道这条，会不会写出**方向性错误**的代码？" → 入选 L1

---

### L2 — INDEX（分类索引层）

**角色**：目录导航

| 维度 | 定义 |
|------|------|
| 内容 | 每个分类的边界定义 + L3 文件列表 + 何时查阅 |
| 不放什么 | 具体规范内容（→L3）、代码示例（→L3/L4） |
| 行数 | ≤50 行/文件 |
| 文件数 | 11 个（按分类编号 00-10） |
| 加载方式 | **逐文件 symlink** 到 `.kiro/steering/`（排除 README.md） |
| 谁维护 | 人类架构师 |
| 更新频率 | 低（新增分类时） |

**为什么逐文件而非整目录链接**：整目录链接会把 README.md 也注入 Kiro，造成无关内容污染上下文。

---

### L3 — CONDENSED（精炼规范层）

**角色**：操作手册

| 维度 | 定义 |
|------|------|
| 内容 | 领域规范要点、代码模式、✅/❌ 示例、禁止用法 |
| 不放什么 | 设计理由（→L4）、操作记录（→L5）、完整实现代码（→L4） |
| 行数 | ≤200 行/文件（目标 100-150，复杂规范可到 200） |
| 文件数 | ~60 个，与 L4 一一对应 |
| 加载方式 | **整目录 symlink** 到 `.cursor/rules/`、`.continue/rules/`、`.windsurf/rules/`、`.claude/memories/` |
| 谁维护 | 人类架构师（主）+ AI 提议 |
| 更新频率 | 中 |

**这是精炼规范的唯一主版本**——修改 L4 后必须同步更新 L3。

L3 文件头必须包含指向 L4 的链接：
```markdown
> Full spec: .ai/L4/standards/03.frontend-01.vue.md
```

---

### L4 — FULL（完整文档层）

**角色**：百科全书

| 维度 | 定义 |
|------|------|
| 内容 | 完整规范文档、参考实现、架构决策记录（ADR）、设计哲学 |
| 不放什么 | 精炼要点（→L2）、操作日志（→L5） |
| 行数 | 无限制 |
| 加载方式 | AI 需要完整信息时手动读取（L2 文件头链接指向 L4） |
| 谁维护 | 人类架构师 |
| 更新频率 | 低-中 |

**L4 子目录分类**：
| 子目录 | 内容 | 命名方式 |
|--------|------|---------|
| `standards/` | L2 的完整展开版 | 编号命名（与 L2 对应） |
| `references/` | 参考实现、代码模板 | 编号命名 `{编号}.ref-{序号}.{主题}.md` |
| `adr/` | 架构决策记录 | ADR 序号命名 `{0001}-{title}.md` |
| `philosophy/` | 设计哲学、命名理念 | 编号命名 `{编号}.philosophy-{序号}.{主题}.md` |

---

### L5 — LOG（操作日志层）

**角色**：黑匣子

| 维度 | 定义 |
|------|------|
| 内容 | 任务完成记录、变更日志、调试过程、会话摘要 |
| 不放什么 | 通用规范（→L2/L4）、功能设计（→L3） |
| 行数 | 无限制 |
| 加载方式 | 正常情况 AI 不读，回溯历史时才读 |
| 谁维护 | AI 自动生成（任务完成后写入） |
| 更新频率 | 极高（每次任务完成后） |
| 核心原则 | **Append-only** — 只追加，不修改，不删除 |

**文件命名**：`{YYYY-MM-DD}.{type}-{topic}.md`

**日志类型**：
- `task` - 任务完成记录
- `debug` - 调试过程记录
- `decision` - 架构决策记录
- `session` - 会话摘要记录

**终极价值**：如果 L0-L4 全部丢失，在不考虑算力的情况下，可以从 L5 日志逐步蒸馏重建全部层级。

**重建路径**：
```
L5（原始日志）
  → 提取规律和规则 → L4（重建完整规范）
    → 提取当前状态 → L3（重建功能上下文）
      → 蒸馏要点 → L2（重建模块规范）
        → 提取核心 → L1（重建基石规则）
          → 生成索引 → L0（重建引导）
```

---

### L6 — GRAPH（知识图谱层）**可选扩展**

**角色**：语义搜索引擎

| 维度 | 定义 |
|------|------|
| 内容 | 碎片化知识存储、向量嵌入、语义关联 |
| 技术选型 | FalkorDB / Neo4j / 其他图数据库 |
| 访问方式 | 通过 MCP 工具（如 Graphiti MCP） |
| 谁维护 | AI 自动积累（从 L4/L5 提取） |
| 更新频率 | 持续积累 |
| 核心原则 | **越大越好** — 知识积累越丰富，搜索越精准 |

**核心价值**：
- **语义搜索** - 通过向量相似度精准获取相关知识片段
- **节省 Token** - 无需读取完整文档，只获取相关片段（节省 90%+）
- **历史积累** - 随着开发推进，知识图谱越来越丰富
- **跨会话记忆** - 保留历史架构决策和开发经验

**使用场景**：
- 精炼规范（L3）不够详细时
- 需要查找历史决策或经验时
- 需要跨文档关联信息时

**集成方式**：
```
L4/L5 内容
    ↓ 提取关键信息
向量嵌入（如 text-embedding-3-small）
    ↓ 存储到图数据库
L6 知识图谱
    ↓ 语义搜索
通过 MCP 工具查询
```

**注意**：L6 是可选扩展层，不是必需的。小型项目可以只使用 L0-L5。

### 映射关系

```

    ↓ gogogo.sh 8 / sync.sh

CLAUDE.md              ← symlink → .ai/L1/00.overview.md
.cursorrules           ← symlink → .ai/L1/00.overview.md
.windsurfrules         ← symlink → .ai/L1/00.overview.md
.kiro/steering/        ← 真实目录，逐文件 symlink → .ai/L2/*.md（排除 README.md）
.cursor/rules/         ← 真实目录，逐文件 symlink → .ai/L2/*.md（排除 README.md）
.claude/memories/      ← 真实目录，逐文件 symlink → .ai/L2/*.md（排除 README.md）
.continue/rules/       ← 真实目录，逐文件 symlink → .ai/L2/*.md（排除 README.md）

.kiro/specs/           ← 逐文件 symlink → .ai/L0/specs/
.cursor/specs/         ← 逐文件 symlink → .ai/L0/specs/
...
```

### 关键设计决策

**所有工具的 rules 目录都只自动载入 L2（11个分类索引）**：
- L2 是轻量的分类索引（≤50行/文件），适合每次对话自动载入
- L3 精炼规范（≤200行/文件）通过 `globs` frontmatter 按需触发，不默认全量载入
- 所有工具统一用逐文件链接，排除 README.md，避免无关内容污染上下文

### gogogo.sh 8 子命令

```bash
./gogogo.sh 8a   # 映射到 Kiro
./gogogo.sh 8b   # 映射到 Cursor
./gogogo.sh 8c   # 映射到 Claude Code
./gogogo.sh 8d   # 映射到 Windsurf
./gogogo.sh 8e   # 映射到 Continue
./gogogo.sh 8f   # 映射到所有工具
./gogogo.sh 8g   # 移除所有映射（并检查非链接文件）
```

## 读写流程

### AI 读取流程（由浅入深）

```
对话开始
    ↓
工具自动加载 L1（AGENTS.md / CLAUDE.md / .cursorrules 等）= 概览+零容忍规则
    ↓
Kiro 自动加载 L2（.kiro/steering/）= 分类索引，知道去哪找规范
    ↓
工具自动从 rules 目录加载 L3 = 按 scope 匹配的精炼规范
    ↓
如需功能上下文 → 读 L0/specs/active/ = 当前功能的 spec
    ↓
如需完整信息 → 读 L4 = 完整规范原文
    ↓
如需回溯历史 → 读 L5 = 操作日志（极少）
```

### 人类写入流程（由深到浅）

```
人类修改规范
    ↓
1. 先改 L4（完整规范，保留所有细节）
    ↓
2. 从 L4 蒸馏到 L2（提取核心要点，≤150 行）
    ↓
3. 如影响核心架构 → 更新 L1
    ↓
4. 如涉及架构决策 → 在 L4/adr/ 添加 ADR
    ↓
5. symlink 自动同步到各工具（无需手动 cp）
```

### AI 任务完成流程（自动写 L5）

```
AI 完成任务
    ↓
自动在 L5 写入日志：
  - 文件名：{YYYY-MM-DD}.{type}-{topic}.md
  - 内容：任务描述 + 变更清单 + 关键决策 + 遇到的问题
    ↓
如任务涉及规范变更 → 提议更新 L2/L4（人类审核）
```

## 未来扩展点

七层体系为以下增强工具预留了集成点：

| 工具 | 集成位置 | 用途 |
|------|---------|------|
| Graphiti (MCP) | L6 | 时序知识图谱，跨会话架构记忆 |
| Qdrant MCP | L6 | 代码语义搜索 |
| Context7 MCP | L2 加载时 | 实时注入库文档（指定版本） |
| Repomix | L4 辅助 | 打包代码库为 AI 可读格式 |
| Roo Code Memory Bank | L3 | 结构化进度追踪 |

这些工具的引入不改变七层结构本身，只是在特定层级增加数据源或检索能力。
