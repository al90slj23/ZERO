1. **Hooks 配置规范**（针对支持 hook 的 IDE）

**核心理念**：规范同步冲突检测是一套**开发方法论**，不依赖特定工具。有 hook 能力的 IDE 自动触发，无 hook 能力的环境手动执行。

## 🏛️ Hook 架构原则

### 核心原则（零容忍）

`.kiro/hooks/` 等 IDE 配置目录是**只读映射目标**，禁止直接在其中创建或修改文件。

```
❌ 禁止：直接在 .kiro/hooks/ 创建文件
✅ 正确：在 .ai/L0/hooks/kiro/ 创建，再运行映射命令
```

### 目录结构

```
.ai/L0/                          ← 源文件（唯一可编辑位置）
  hooks/
    kiro/                        ← Kiro hook 源文件（统一 .json）
      standards-sync-on-complete.json
      pre-commit-typecheck.json
    husky/                       ← Git hook 源文件
    ide/                         ← 其他 IDE hook 源文件

.kiro/                           ← 映射目标（只读，符号链接）
  hooks/
    standards-sync-on-complete.kiro.hook  → .ai/L0/hooks/kiro/standards-sync-on-complete.json
    pre-commit-typecheck.kiro.hook        → .ai/L0/hooks/kiro/pre-commit-typecheck.json
```

### 文件格式规范

**源文件扩展名**：统一用 `.json`（人类友好，IDE 有语法高亮）

**映射后扩展名**：自动重命名为 `.kiro.hook`（Kiro 要求）

`gogogo.ai.sh` 在映射时自动完成 `{name}.json` → `{name}.kiro.hook` 的重命名，无需手动处理。

**必须字段**：

```json
{
  "version": "1.0.0",
  "enabled": true,
  "name": "hook名称",
  "description": "hook描述",
  "when": { "type": "agentStop" },
  "then": {
    "type": "askAgent",
    "prompt": "..."
  }
}
```

**关键点**：
- `enabled: true` 是必须字段，缺少则 Kiro 不显示该 hook
- Kiro **支持 symlink**，映射用 `ln -sf` 即可
- 源文件用 `.json`，映射目标自动变成 `.kiro.hook`

## 🚨 规范同步冲突检测（开发方法论级）

### 设计理念

**核心价值**：通过每次规范变更，触发全局冲突检测，逐步收敛到一致性。

**工作原理**：

```
触发点（某个规范需要调整）
    ↓
启动冲突检测流程
    ↓
横向扫描：L4 内所有相关文档（找出历史矛盾）
    ↓
纵向对比：L4 → L3 → L2 → L1（找出层级不一致）
    ↓
列出所有冲突点 → 等待用户确认
    ↓
批量修正（不只是改一个文件，而是同步所有关联文档）
```

**最终效果**：

每次规范调整 = 一次全局纯化，经过多次迭代后：
- ✅ 所有文档规范一致
- ✅ 没有历史遗留的矛盾描述
- ✅ 新旧规范不会并存
- ✅ AI 读取任何文档都能得到正确指引

### 实施方式

#### 方式 1：自动触发（支持 hook 的 IDE）

**适用环境**：Kiro、Claude Code、OpenCode 等支持 hook 的 IDE

**配置文件**：`.ai/L0/hooks/kiro/standards-sync-on-complete.json`

**完整配置**：

```json
{
  "version": "1.0.0",
  "enabled": true,
  "name": "规范同步检查",
  "description": "任务完成后，检查是否涉及规范变更，若有则强制执行 L4→L3→L2→L1 全链路同步",
  "when": {
    "type": "agentStop"
  },
  "then": {
    "type": "askAgent",
    "prompt": "任务刚刚完成。请立即执行规范同步自检（含冲突检测）：\n\n## 第一步：判断是否涉及规范变更\n本次任务是否涉及任何规范、架构、数据库表结构、API设计、命名规则的新增或变更？\n- 如果否 → 回复「本次无规范变更」即可\n- 如果是 → 继续第二步\n\n## 第二步：冲突检测（必须执行）\n针对本次变更的主题（如：数据完整性、API命名、背包分表等），严格按以下顺序排查：\n\n1. **L4 内部冲突检测**（.ai/L4/standards/）\n   - 搜索所有相关 md 文件中关于本次主题的描述\n   - 列出所有矛盾点（如：A文件说「必须分表」，B文件说「可以合表」）\n   - 询问：「L4 发现冲突：[具体描述]，是否以本次最新规范为准？」\n\n2. **L3 与 L4 一致性检测**（.ai/L3/ vs .ai/L4/）\n   - 对比 L3 精炼规范是否与 L4 完整规范矛盾\n   - 列出不一致点（如：L4 要求字段顺序，L3 未提及）\n   - 询问：「L3-L4 冲突：[具体描述]，是否需要同步？」\n\n3. **L2/Kiro 与 L3 一致性检测**（.kiro/steering/ vs .ai/L3/）\n   - 检查 Kiro steering 的「何时查阅」索引是否覆盖本次主题\n   - 列出缺失或过时的索引项\n   - 询问：「L2 索引缺失：[具体描述]，是否需要补充？」\n\n4. **L1 宪法级检测**（.ai/L1/00.overview.md + AGENTS.md）\n   - 仅当本次变更属于「零容忍规则」级别时才更新\n   - 列出需要加入 L1 的宪法级规则\n   - 询问：「L1 宪法级变更：[具体描述]，是否需要写入零容忍规则？」\n\n## 第三步：执行同步（确认后）\n用户确认冲突处理方案后，按 L4→L3→L2→L1 顺序更新所有层级。\n\n**重要**：不要自动修复冲突，必须先列出所有矛盾点并等待用户确认。"
  }
}
```

#### 方式 2：手动执行（不支持 hook 的环境）

**适用环境**：Cursor、CLI、其他不支持 hook 的 IDE

**执行时机**：每次完成涉及规范变更的任务后，手动执行以下流程

**执行流程**：

##### 第一步：判断是否涉及规范变更

本次任务是否涉及任何规范、架构、数据库表结构、API设计、命名规则的新增或变更？
- 如果否 → 无需执行冲突检测
- 如果是 → 继续第二步

##### 第二步：冲突检测（必须执行）

针对本次变更的主题，严格按以下顺序排查：

**1. L4 内部冲突检测**

搜索 `.ai/L4/standards/` 或 `.ai/L4/standards/` 中所有相关 md 文件，列出矛盾点：

```bash
# 示例：搜索「背包」「道具」「分表」相关描述
grep -r "背包\|道具\|分表" .ai/L4/standards/
```

发现冲突后，询问：「L4 发现冲突：[具体描述]，是否以本次最新规范为准？」

**2. L3 与 L4 一致性检测**

对比 `.ai/L3/` 或 `.ai/L3/` 与 L4 对应文件，列出不一致点：

```bash
# 示例：对比 L3 和 L4 的同名文件
diff .ai/L3/01.arch-07.data-integrity.md .ai/L4/standards/01.arch-07.data-integrity.md
```

发现不一致后，询问：「L3-L4 冲突：[具体描述]，是否需要同步？」

**3. L2 索引一致性检测**

检查 `.ai/L2/` 或 `rules/README.md` 索引是否覆盖本次主题：

```bash
# 示例：检查索引中是否提及本次主题关键词
grep "背包\|道具" .ai/L2/09.tool.md
```

发现缺失后，询问：「L2 索引缺失：[具体描述]，是否需要补充？」

**4. L1 宪法级检测**

判断本次变更是否属于「零容忍规则」级别：

```
符合条件：
- 涉及核心架构原则
- 违反会导致严重后果
- 需要全员强制遵守
```

符合条件后，询问：「L1 宪法级变更：[具体描述]，是否需要写入零容忍规则？」

##### 第三步：执行同步（确认后）

用户确认冲突处理方案后，按以下顺序更新：

```
1. 更新 L4 所有冲突文件（统一口径）
2. 同步 L3 对应文件（提取核心要点）
3. 更新 L2 索引（补充缺失主题）
4. 更新 L1 零容忍规则（如需要）
5. 运行 ./gogogo.sh ai（同步到所有 IDE）
```

## 🔧 新增 Hook 流程（仅适用支持 hook 的 IDE）

### 1. 创建源文件

```bash
# 在 L0 源目录创建文件（统一用 .json）
touch .ai/L0/hooks/kiro/my-new-hook.json
```

### 2. 编辑配置

```json
{
  "version": "1.0.0",
  "enabled": true,
  "name": "我的新 Hook",
  "description": "Hook 描述",
  "when": {
    "type": "agentStop"
  },
  "then": {
    "type": "askAgent",
    "prompt": "..."
  }
}
```

### 3. 映射到 IDE

```bash
# 运行映射命令
./gogogo.sh ai
```

### 4. 验证

```bash
# 检查符号链接是否创建成功
ls -la .kiro/hooks/my-new-hook.kiro.hook
```

## 📋 Hook 类型（仅适用支持 hook 的 IDE）

### 1. agentStop（任务完成后）

**用途**：任务完成后自动触发

**示例**：规范同步检查

```json
{
  "when": { "type": "agentStop" },
  "then": {
    "type": "askAgent",
    "prompt": "任务完成，请执行自检..."
  }
}
```

### 2. userTriggered（手动触发）

**用途**：用户手动触发

**示例**：提交前类型检查

```json
{
  "when": { "type": "userTriggered" },
  "then": {
    "type": "runCommand",
    "command": "npm run type-check"
  }
}
```

### 3. fileEdited（文件编辑后）

**用途**：文件保存后自动触发

**示例**：Vue 文件变更后同步数据库

```json
{
  "when": {
    "type": "fileEdited",
    "patterns": ["*.view.vue"]
  },
  "then": {
    "type": "runCommand",
    "command": "php artisan view:sync && php artisan view:validate"
  }
}
```

### 4. preToolUse（工具使用前）

**用途**：工具调用前自动触发

**示例**：写入操作前确认

```json
{
  "when": {
    "type": "preToolUse",
    "toolTypes": ["write"]
  },
  "then": {
    "type": "askAgent",
    "prompt": "请确认此写入操作符合规范..."
  }
}
```

## 🚨 强制执行规范

### 1. 禁止直接修改映射目标

```
❌ 禁止：直接在 .kiro/hooks/ 创建或修改文件
✅ 正确：在 .ai/L0/hooks/kiro/ 创建，再运行 ./gogogo.sh ai
```

### 2. 规范同步冲突检测不可跳过

**有 hook 能力的 IDE**：规范同步 Hook 必须启用（`enabled: true`）

**无 hook 能力的环境**：每次规范变更后必须手动执行冲突检测流程

### 3. 冲突检测必须完整执行

规范同步冲突检测触发后，必须完成四步检测流程，不可直接修改文件。

### 4. 用户确认后才执行同步

不要自动修复冲突，必须先列出所有矛盾点并等待用户确认。

## 📌 核心原则

### 架构原则

1. **`.ai/L0/hooks/kiro/` 是 Hook 唯一主版本**
2. **`.kiro/hooks/` 是只读映射目标**，禁止直接修改
3. **所有 Hook 通过 gogogo.sh ai 同步**
4. **源文件用 .json，映射后自动变成 .kiro.hook**

### 规范同步原则（开发方法论级）

1. **每次规范变更 = 一次全局纯化**
2. **横向扫描 L4 内部冲突**
3. **纵向对比 L4→L3→L2→L1 一致性**
4. **用户确认后才执行同步**
5. **逐步收敛到一致性**
6. **不依赖特定工具**：有 hook 自动触发，无 hook 手动执行

### 冲突检测原则

1. **不要自动修复冲突**
2. **列出所有矛盾点**
3. **等待用户确认**
4. **批量修正所有关联文档**
