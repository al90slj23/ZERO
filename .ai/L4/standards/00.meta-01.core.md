# 00.meta-01.core - 元规范

> **文档版本**：v1.0.0
> **创建日期**：2025-12-30

---

## 📍 文档定位

定义开发规范的规范，包含文档体系架构、文档命名规范、读取/写入顺序。

---

## 🏗️ 文档体系架构

### 三层体系

```
浓缩版（README.md）← 入口导航
   ↑ 提炼
精炼版（condensed/）← AI 优先读取，100-150行/文件
   ↑ 提炼
完整版（standards/）← 人类阅读，无行数限制
```

### 文档分类

| 类型 | 位置 | 读者 | 特点 |
|------|------|------|------|
| 浓缩版 | `README.md` | AI+人类 | 导航索引，≤1000行 |
| 完整版 | `.ai/L4/standards/` | 人类 | 原则性、无限制 |
| 精炼版 | `.ai/L3/` | AI | 核心要点，100-150行 |

## 📋 规范文档命名规范

### 命名格式

```
{大类编号}.{类别}-{序号}.{主题}.md
```

**格式解析**：
- **大类编号**（2位数字）：规范的大分类，如 `00`、`01`、`02`
- **类别**（英文）：大类的英文名称，如 `meta`、`arch`、`backend`
- **序号**（2位数字）：该类别下的文档序号，如 `01`、`02`、`03`
- **主题**（英文）：具体主题名称

### 大类编号定义

| 编号 | 类别 | 说明 |
|------|------|------|
| 00 | `meta` | 元规范（规范的规范） |
| 01 | `arch` | 架构规范 |
| 02 | `backend` | 后端规范 |
| 03 | `frontend` | 前端规范 |
| 04 | `quality` | 质量规范 |
| 05 | `biz` | 业务规范 |
| 06 | `data` | 数据规范 |
| 07 | `security` | 安全规范 |
| 08 | `ops` | 运维规范 |
| 09 | `tool` | 工具规范 |
| 10 | `ref` | 参考规范 |

### 命名举例

```
00.meta-01.core.md              # 大类00 + 类别meta + 序号01 + 主题core
01.arch-01.core.md              # 大类01 + 类别arch + 序号01 + 主题core
01.arch-02.structure.md         # 大类01 + 类别arch + 序号02 + 主题structure
02.backend-01.api.md            # 大类02 + 类别backend + 序号01 + 主题api
02.backend-02.db-tables.md      # 大类02 + 类别backend + 序号02 + 主题db-tables
03.frontend-01.structure.md     # 大类03 + 类别frontend + 序号01 + 主题structure
04.quality-01.naming.md         # 大类04 + 类别quality + 序号01 + 主题naming
```

### 子主题命名（多级扩展）

当一个主题有多个子文档时，在主题后继续用 `-{子序号}` 扩展：

```
02.backend-03.db-01.tables.md       # backend第03号主题db，子主题01-tables
02.backend-03.db-02.fields.md       # backend第03号主题db，子主题02-fields
02.backend-03.db-03.field-01.naming.md  # 更深层级：field的子主题01-naming
02.backend-03.db-03.field-02.order.md   # 更深层级：field的子主题02-order
```

### 数字含义总结

| 位置 | 含义 | 举例 |
|------|------|------|
| 第1段数字 | 大类编号 | `02` = 后端规范 |
| 第2段数字 | 类别内序号 | `03` = 该类别第3个主题 |
| 第3段数字 | 子主题序号 | `01` = 该主题第1个子文档 |
| 第4段数字 | 更深层级 | `02` = 更细分的子主题 |

## 📏 行数限制规范

| 层级 | 推荐 | 上限 | 警告 | 禁止新增 |
|------|------|------|------|---------|
| **完整版** | - | - | - | - |
| **精炼版** | 100 | 150 | 200 | 250 |
| **浓缩版** | 800 | **1000** | - | - |

### 紧缩策略（触碰行数限制时）

**核心原则**：限制行数不是删减内容，而是倒逼格式紧缩。

| 优先级 | 策略 |
|--------|------|
| 1 | 删除多余空行 |
| 2 | 合并短行 |
| 3 | 精炼语言 |
| 4 | 表格化 |
| 5 | 符号替代（"大于等于" → "≥"） |
| 6 | 删除装饰性符号 |

**禁止**：删除实质性内容

## ✏️ 规范更新工作流

### 写入顺序（保障完整性）

```
1️⃣ standards/   ← 优先保存完整信息
        ↓
2️⃣ condensed/   ← 提取核心要点（100-150行）
        ↓
3️⃣ README.md    ← 更新导航索引（如需要）
```

### 读取顺序（节省 Token）

```
1️⃣ condensed/   ← AI 优先读取精炼版
        ↓ 精炼版不够时
2️⃣ standards/   ← 读取完整版
```

---

## 🚨 强制执行规范

### 修改完成自检

每次修改 `standards/` 后必须：
1. 同步更新 `condensed/` 对应文件
2. 更新 `README.md` 导航索引（如需要）

### 新增规范检查清单

- [ ] 文件命名符合 `{分类编号}.{类别}-{序号}.{主题}.md` 格式
- [ ] 分类编号正确
- [ ] 创建对应的 `condensed/` 精炼版
- [ ] 更新 `README.md` 文档结构

---

## 📌 核心原则

1. **`standards/` 是完整规范主版本**
2. **`condensed/` 是精炼规范主版本**
3. **`README.md` 是导航索引**
4. **写入时完整版优先，读取时精炼版优先**
